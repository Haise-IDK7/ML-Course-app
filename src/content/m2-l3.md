Entrenar el modelo es la parte más corta de un proyecto real. Lo que decide si funciona suele estar antes (los datos) y después (cómo se evalúa). Este es el recorrido completo.

@fig(flujo | Un proyecto de ML es un ciclo, no una línea recta.)

## Los pasos

**1. Definir el problema.** ¿Qué se predice exactamente, a partir de qué, y cómo se medirá el éxito? «Detectar fraude» no es una definición; «marcar transacciones para revisión manual detectando al menos el 90 % de los fraudes con menos de un 5 % de falsas alarmas» sí lo es. Decide también la **línea base**: la regla sencilla que tu modelo debe superar (predecir siempre la clase más frecuente, usar la media).

**2. Reunir los datos.** Cada ejemplo se describe con **características** (las variables de entrada) y, si el problema es supervisado, una **etiqueta**. Los datos deben parecerse a los que el modelo encontrará cuando se use.

**3. Preparar y dividir.** Limpiar errores, tratar valores ausentes, convertir categorías en números y poner las características en escalas comparables. Y, sobre todo, **dividir**.

@fig(split | El conjunto de prueba se guarda bajo llave hasta el final.)

::: def Los tres conjuntos
- **Entrenamiento:** el modelo ajusta sus parámetros con estos datos.
- **Validación:** sirve para comparar variantes y elegir **hiperparámetros** (ajustes que no se aprenden, como la tasa de aprendizaje o el número de capas).
- **Prueba:** se usa **una sola vez**, al final, para estimar el rendimiento sobre datos nunca vistos.
:::

¿Por qué tres y no dos? Porque cada vez que eliges un hiperparámetro mirando el resultado en validación, te estás adaptando un poco a esos datos. Tras cincuenta decisiones, el resultado de validación es optimista. El conjunto de prueba, intacto, es la única estimación honesta.

**4. Entrenar.** Elegir un tipo de modelo y ajustar sus parámetros minimizando una función de pérdida.

**5. Evaluar.** Medir en validación con una métrica que refleje el objetivo real. Si no es suficiente, volver atrás: más datos, mejores características, otro modelo.

**6. Desplegar y vigilar.** El mundo cambia y los datos nuevos se van alejando de los de entrenamiento (deriva de datos), así que el rendimiento se degrada y hay que reentrenar.

## El error más caro: la fuga de datos

::: def Fuga de datos
Hay **fuga de datos** cuando información que no estará disponible al predecir se cuela en el entrenamiento. El modelo parece excelente en las pruebas y falla en el uso real.
:::

::: ejemplo Tres fugas típicas
1. **Preprocesar antes de dividir.** Si calculas la media y la desviación con *todos* los datos para estandarizar y después divides, el conjunto de prueba ya ha influido en el entrenamiento. Lo correcto: dividir primero y calcular las estadísticas solo con el entrenamiento.
2. **Duplicados o parientes.** Varias radiografías del mismo paciente repartidas entre entrenamiento y prueba: el modelo reconoce al paciente, no la enfermedad. Hay que dividir por paciente.
3. **Mirar al futuro.** En series temporales, dividir al azar mezcla el futuro con el pasado. Hay que entrenar con lo anterior y probar con lo posterior.
:::

::: ojo Desconfía de un resultado demasiado bueno
Un 99.9 % de aciertos en un problema difícil casi nunca es un gran modelo: casi siempre es una fuga. Antes de celebrarlo, busca cómo podría el modelo estar «haciendo trampa».
:::

## Parámetros frente a hiperparámetros

| | Parámetros | Hiperparámetros |
|---|---|---|
| Quién los fija | el entrenamiento | tú, antes de entrenar |
| Ejemplos | pesos y sesgos | tasa de aprendizaje, número de capas, $k$ en k-NN |
| Con qué datos | entrenamiento | validación |

::: resumen
- Define el objetivo y una línea base antes de tocar un modelo.
- Divide en entrenamiento, validación y prueba; la prueba se usa una sola vez.
- Calcula cualquier estadística de preprocesado solo con el entrenamiento.
- La fuga de datos produce métricas espectaculares y modelos inútiles.
- Los parámetros se aprenden; los hiperparámetros se eligen con validación.
:::
